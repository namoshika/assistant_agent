# テスト規約

## テスト階層

- **単体テスト** (`tests/unit/`): Claude Code が実装時に自動実行する。外部システム不要。
- **統合テスト** (`tests/integration/`): Claude Code は実装時に `--collect-only` を付与し自動実行する事で構文チェックする (実際の実行はしない)。実際の実行は人間が検収時に手動実行する (PostgreSQL / Gemini API が必要)。

## 主要ファイル

| ファイル | 役割 |
|---|---|
| `tests/unit/` | 単体テストコード |
| `tests/integration/` | 結合テストコード |
| `tests/data` | テストデータ |

## 単体テスト方針

- 単体テストはクラスが外部に対して持つ機能を対象に行う（細かい内部ロジックに対する単体テストは行わない）
- 内部メソッド (メソッド名が `_` から始まるメソッド) に対する単体テストは行わない
- 単体テストする際に対象クラスはモック化しない (参照する外部のインスタンスやクラスをモック化する)

## 統合テスト方針

- 実際の外部システムに接続し、エンドツーエンドの動作を確認する
- `@pytest.mark.integration` デコレータを各テスト関数に付与する
- 複数テストファイルで共有するフィクスチャは `tests/integration/conftest.py` に定義する。テストファイル固有のフィクスチャは各テストファイルに定義する
- 環境変数未設定時は `pytest.fail()` でテスト失敗にする

## 構造

- **テストクラス**: テスト対象クラス単位で `Test{TargetClassName}` の命名で作成する
- **テストメソッド**: テスト対象メソッド単位で `test_{target_method_name}_{連番:02}` の命名で作成する。
  - **注意:** 連番は少なく抑え、必要な場合 (検証するインスタンスが異なるなど) のみ追加する。
  - **注意:** 同一フィクスチャインスタンスで複数シナリオを検証できる場合は1つのテストメソッドに統合する

## テストメソッドの書き方

- モックには `MockerFixture`, `unittest.mock.MagicMock` を使用する
- テスト用インスタンス生成ヘルパーはテストクラス内の `@staticmethod` として定義する
- テスト用コードは簡潔な記述をすること
  - 共通: コメントで docstring と同じことを書かない
  - モジュール: コメント, docstring を書かない
  - クラス: テスト対象が一つの場合はモジュールにテストメソッドを直接定義 (テストクラスを作成しない)
  - メソッド: インデントレベルを低く抑える。フラットなインデントでは複雑さや視認性が悪化する時のみインデントレベルを上げる

```python
def test_some_method_01(mocker: MockerFixture):
    """メソッドの動作説明。

    観点1: ...
    観点2: ...
    """
    # 試験準備
    ...

    # 試験実施
    ...

    # 結果検証
    # 観点1: ...
    assert ...
    # 観点2: ...
    assert ...
```
