# Agent Assistant

月次ニュースを PostgreSQL ベクターストアに格納し、 LLM + LangChain ツールで検索・回答する RAG エージェント。mlflow を通じてデプロイされる。

## Commands

```bash
# テスト実行
uv run pytest tests/ -m 'not integration' -v
uv run pytest tests/ -m 'integration' -v --collect-only

# lint 実行 (適用 rule は pyproject.toml に記載)
uvx ruff check
```

### 主要ディレクトリ

| ディレクトリ | 役割 |
|---|---|
| `docs/adr/` | 過去のアーキテクチャ検討における方針の変遷を記録。開発時の設計を検討する上で、過去の経緯を考慮するのに使用。 |
| `docs/experimental/` | 個々の開発時の検討資料や設計、タスクリスト。中断した作業の再開に使用。 |
| `script/` | 開発者の作業用のノートブック |
| `src/` | 開発中のソースコード |
| `tests/` | テストコード |
| `tests/data` | テストデータ |

## ワークフロー
Claude Code は 機能追加を以下の流れで行い、都度状況を `docs/experimental/{date}_{task_name}/` へ記録する。ステップ2以降は `tasks.md` に記載したタスクを順に実行 (※ 背景1)。完了したタスクにはチェックを付ける。各ステップでは **品質を優先** せよ (※ 背景2)。  

**※ 背景1:** エージェントの性能が落ち、コンテキスト消費の増大に原因が有ると思われる場合に、作業を中断し新しいセッションで再開させることが有ります。その際の再開に必要な情報を記録させます。  
**※ 背景2:** 速く進める事よりも、品質低下を招く事柄 (要件反映やタスクの実施漏れ) を避ける方針を取る。

1. 設計: 改修を要求されたら以下を検討。承諾されたら一連のファイルを書き出す
    - 要件定義 (`requirements.md`): 抽出された要件を記載 (テンプレート: `docs/templates/requirements.md`)。
      理由・経緯・現状描写は含めない（design.md に委ねる）
    - 方法検討 (`research.md`, テンプレート: `docs/templates/research.md`): web で事例や資料を読み、 `docs/adr/` の記録を考慮しつつ用いる方法やライブラリを決定。理由・実装に必要なサンプルやリファレンスのURLを記録。
      調査で分かった客観的事実（API仕様・制約・検証結果）はすべてここに書き、design.md には書かない
    - 設計 (`design.md`): 定めた方法に則り設計 (テンプレート: `docs/templates/design.md`)
    - チェック: 設計を再読し、実装方法や過去の経緯との兼合い、全体とのバランスを確認。必要に応じて既存箇所も改修し、シンプルかつ堅牢な作りとなるよう設計を改善。
    - タスクへ分解 (`tasks.md`): チェック可能な項目でプランを作成
2. 実装: TDD で実装。単体・結合テストも作成 (作成時には `.claude/rules/test_policy.md` を確認)。 ruff により設定されたルールを順守せよ (ルール無効化を禁止)
    - **テストファースト**: すべての実装はテストを先に書いてから行う
    - **Red-Green-Refactor**: このサイクルを厳密に守る
3. 試験: pytest を実行し、試験をパスする

### エラーシナリオ

実装中に問題（依存関係の競合・想定外の制約・設計の齟齬など）が発生した場合、以下を厳守する。

1. **即座に作業を止める** (問題を自己解決しようとしない)
2. **plan モードで修正計画を提示し、承認を得てから再開する**

承認済みの計画から逸脱する変更はすべて再承認が必要。変更の大小・自明さに関わらず例外なく適用する。

- NG 例: ライブラリが入らないので代替ライブラリを使った / 設計を変えて実装した
- OK 例: plan モードで「〇〇の問題が発生したため、△△へ変更したい」と提示して承認を得た

解決策が見当たらない場合は **指示を仰ぐこと**

## 要求解釈

要求文中の固有名詞（クラス名等）が複数の意味を持ちうる場合、フェーズ（設計・実装等）を問わず、着手前にユーザーへ確認すること。

## 記載規約

ドキュメント・設定ファイルに、冗長な理由付け・重複説明・過剰な具体例を書いてはならない。書く・編集するたびに見直し、該当箇所を削ってから確定すること。
